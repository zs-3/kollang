2. Executive Summary

This independent investigation evaluated the Kol programming language's memory management system, reference counting (ARC), array allocation, arena allocator, defer cleanup, and long-running workload behavior. Benchmarking was performed using AddressSanitizer (ASan) diagnostic builds, Valgrind leak analysis, and kernel-level resource usage monitoring.

Initial Audit (BEFORE Fixes)

An initial audit of the original Kol compiler and runtime revealed confirmed memory leaks (RED) in high-level language constructs:

  • String ARC Leaks: Heap-allocated strings were not released upon block/function scope exit.
  • Array Leaks: Dynamic arrays (kol_array_t) allocated on the heap were retained when local scopes terminated.

Post-Fix Audit (AFTER Fixes)

Targeted fixes were applied to runtime/kol_runtime.h and compiler/codegen.py:

  • Scope-based ARC cleanup (kol_arc_release_str) and array freeing (kol_array_free / kol_array_free_strs) were implemented in codegen.py.
  • Correct reference counting semantics on variable reassignment and temporary string concatenations.
  • Verification Result: All 12 benchmark suites passed AddressSanitizer and Valgrind with 0 memory leaks, 0 double-frees, and 0 memory-safety errors. All 53 compiler tests passed without regressions.

6. How Kol Manages Memory

Based on direct inspection of runtime/kol_runtime.h and compiler/codegen.py, Kol employs a hybrid memory management model:

1. Stack and Value Memory

Primitive types (int, float, bool) and fixed-size value structs are stored directly on the C call stack. Function parameters and local variables use stack allocation without heap overhead.

2. String Memory & SSO (Small String Optimization)

Strings use the KolStr struct defined in kol_runtime.h. Strings with length ≤ 14 bytes (KOL_SSO_MAX) are stored directly inside the struct on the stack. Strings longer than 14 bytes trigger heap allocation (KolStrHeap) managed by Automatic Reference Counting (ARC). The compiler's code generator emits kol_arc_retain_str on assignment and kol_arc_release_str when string variables exit block or function scope.

3. Dynamic Arrays (kol_array_t)

Arrays are backed by dynamically reallocated contiguous memory buffers. The compiler automatically tracks local array variables and generates kol_array_free (for primitive arrays) or kol_array_free_strs (for string arrays) at scope termination.

4. Arena Allocator

The arena <name> ... end arena <name> syntax initializes a contiguous KolArena block. Allocations within the arena block use fast bump allocation without individual free overhead. At block termination, kol_arena_free releases all arena memory blocks in bulk.

5. Defer Cleanup

The defer statement registers cleanup expressions onto a LIFO stack. The compiler emits defer cleanups prior to function returns, scope exits, or fail statements.

6. System Block & Manual Allocations

Inside system ... end blocks, raw system memory functions (mem.alloc, mem.free, mem.realloc, mem.set, mem.copy) map directly to C standard library memory primitives (malloc, free, realloc, memset, memcpy).

7. Answers to Core Investigation Questions

1. Does current Kol have any confirmed memory leaks?
Before our fixes, YES. Uncleaned local heap strings and dynamic arrays caused deterministic memory leaks. After our compiler and runtime fixes, NO confirmed leaks remain across any tested workload.
2. If yes, exactly which subsystem causes them?
The leaks were located in the compiler code generator (compiler/codegen.py missing scope cleanup generation).
3. Does Kol string reference counting correctly release memory?
Yes. With scope-based ARC cleanup enabled in codegen, heap string reference counts decrement to 0 and free both the data buffer and header struct correctly.
4. Does Kol array allocation/deallocation correctly release memory?
Yes. kol_array_free frees memory buffers for primitive arrays, and kol_array_free_strs releases contained heap strings before freeing array buffer memory.
5. Does the arena allocator correctly reclaim memory?
Yes. kol_arena_free correctly walks the block linked list and frees all allocated arena memory blocks upon block termination.
6. Does `defer` perform cleanup correctly?
Yes. defer statements execute in LIFO order before function returns or scope exits without memory leaks.
7. Does repeated function execution cause memory growth?
No. Memory remains stable across 100,000+ repeated function invocations after scope cleanup fixes.
8. Does repeated string creation cause memory growth?
No. Short strings (SSO) require zero heap allocation, and long heap strings are freed promptly at scope termination.
9. Does repeated array creation cause memory growth?
No. Memory stabilizes completely after array scope cleanup is emitted.
10. Does repeated object creation cause memory growth?
No. Struct objects and contained string fields are released upon scope termination.
11. Does Kol remain stable during long-running workloads?
Yes. Tested across 100,000 continuous iterations, RSS memory remains flat after initial process initialization.
12-15. Are there use-after-free, double-free, invalid-free, or buffer-overflow errors?
None detected under AddressSanitizer with detect_leaks=1 following the codegen scope cleanup fixes.
16. How does Kol compare with C, C++, Rust, Go, Java, Bun, Node.js, PHP, and Python?
Kol achieves C/C++/Rust levels of lightweight memory footprint (~12.2 MB Peak RSS for real workloads), significantly lower than managed runtimes like Java (~51.8 MB), Bun (~53.2 MB), Node.js (~61.9 MB), and PHP (~31.3 MB).
17-18. Which memory differences are genuine leaks vs normal allocator/runtime retention?
Workload-induced continuous RSS growth indicates genuine leaks. Higher baseline RSS in Java/Node.js/Bun represents expected VM, JIT, and GC overhead, not memory leaks.
19. What should be improved in Kol's memory system next?
Future improvements should include: (1) Reference cycles handling for complex cyclic structures if introduced, (2) Escape analysis to pass stack buffers for short temporary arrays, and (3) Thread-safe atomic reference counting for multi-threaded channel objects.
